## 問題点詳細

### Ⅰ. 評価関数の精度問題（5 件）

#### 1. **末端評価ギャップ（ブランダー 3000-5000 スコア差）**

**現象**: ベンチマーク（report-2026-02-14-3、1000試合）でブランダー総数 ~2,800件、うち60% が 3000-5000 スコア差。

**根本原因** (`boardEvaluation.ts` vs `positionEvaluation.ts`):

| 関数                 | 四+活三スコア                 | 用途                     | 検出対象             |
| -------------------- | ----------------------------- | ------------------------ | -------------------- |
| `evaluatePosition()` | 1500+1000+**5000** = **7500** | 手オーダリング (depth>0) | **ミセ手も加算**     |
| `evaluateBoard()`    | 1500+1000 = **2500**          | 末端評価 (depth=0)       | **既存パターンのみ** |

**問題の本質**: `evaluateBoard()` は盤上の既存石のパターンスコアしか見ず、「次の1手で四三が作れる」という **前策脅威（Mise Threat）** を認識しない。

**具体例** (`boardEvaluation.ts` L90-100):

```typescript
function scanFourThreeThreat(board, color, stoneCount) {
  if (stoneCount < 5) return false;
  for (let r = 0; r < 15; r++) {
    for (let c = 0; c < 15; c++) {
      if (board[r]?.[c] !== null) continue; // 空き点のみ
      if (createsFourThree(board, r, c, color)) {
        return true; // 見つけたら即座に +2000 LEAF_FOUR_THREE_THREAT を加算
      }
    }
  }
  return false;
}
```

**既試行**: `LEAF_COMPOUND_THREAT_BONUS` (2026-02-14) は失敗

- 試みた条件: 「同一石が四+活三の両方」→ 既に勝ってる局面のみをさらに高く評価
- 効果: 3000-5000 範囲でゼロ（leaf-eval-gap-analysis.md 参照）

**改善候補**:

- **A. Mise判定の精密化**: `evaluateBoard()` の `scanFourThreeThreat()` に、`positionEvaluation.ts` の `isMiseMove()` 同等の判定を統合
- **B. 最小深度引き上げ**: depth 0 を廃止し、全末端で depth 1 探索（コスト増大リスク）
- **C. 保守的ボーナス値**: `FOUR_THREE_BONUS(5000)` でなく、末端専用の控えめな値から開始

**期待効果**: 3000-5000 スコア差ブランダーを 20-30% 削減、プレイヤーの即敗を回避

**リスク**: 計算コスト増加（scanFourThreeThreat は全空き点走査）

**優先度**: ⭐⭐⭐ （高）

#### 2. **パターン連携度の過小評価**

**現象**: 盤面上の複数石が多方向に活発なパターン（活三×複数、四+活三など）を持つ場合、各パターンスコアの単純加算では **戦術的な威力を過小評価**。

**コード位置** (`boardEvaluation.ts`, `positionEvaluation.ts`):

- `CONNECTIVITY_BONUS: 30` （末端評価）は活三 1 個分（OPEN_THREE: 1000）の 3% にすぎない
- `evaluatePosition()` では `evaluateMultiThreat()` で複数方向脅威に +500 ボーナスを加算

**設計の根拠**:

- 連携度が高い石配置は「次手で四三・VCF・VCT」に発展しやすい
- ただし末端評価では手番不明なため、depth>0 評価より保守的に扱うべき

**問題点**:

- `CONNECTIVITY_BONUS: 30` は仮置き石 1 個での計算。既存の複数パターンの連携度を反映してない
- 例: 活三 2 個（同一石経由）+ 四 1 個 → 三視点では 1000+1000+1500=3500 だが、実際の「複合脅威」度は数倍高い可能性

**改善候補**:

- `CONNECTIVITY_BONUS` を段階的に調整（30 → 50-80）
- または、`evaluateBoard()` で複数方向パターンを検出し、専用ボーナス（`LEAF_MULTI_THREAT_BONUS`）を加算
- `positionEvaluation.ts` の `MULTI_THREAT_BONUS(500)` と整合させる

**期待効果**: 複合脅威下の着手判定精度向上、プレイヤー活三への気づきアップ

**コスト**: 中（パターン走査は既実装）

**優先度**: ⭐⭐ （中）

#### 3. **跳び三・跳び四の防御価値の過小評価**

**現象**: プレイヤーの跳び三を見逃す。「連続三なのに評価が低い」という報告あり。

**根因分析** (`directionAnalysis.ts`, `jumpPatterns.ts`):

```typescript
// 跳び四: 連続四と同等スコア = FOUR(1500)
// 跳び三: 連続三と同等スコア = OPEN_THREE(1000)
// → ただし検出条件が厳しい（制約ライン + 禁手回避必須）
```

**検出ロジックの問題** (`jumpPatterns.ts` L35-67):

1. `isValidConsecutiveThree()` で達四点を全チェック
2. 各達四点で `checkForbiddenMove()` → 禁手なら continue
3. 禁手なし達四点で `checkStraightFour()` 検証

→ **禁手が複数あると、すべてスキップ = 三が無効化される** 可能性

**防御側評価の不均衡**:

- `evaluatePosition()` で相手の活三に防御スコア加算（`applyDefenseMultiplier()`）
- しかし跳び三の防御価値は連続三と同じスコアなのに、検出失敗が多い

**改善候補**:

- 制約ライン検証（`getConsecutiveThreeStraightFourPoints` 呼び出し）の簡略化
- または、禁手以外の達四点で四成立すれば三を有効認定
- 防御側の跳び三検出を強化（`detectOpponentThreats()` で厳密性を高める）

**期待効果**: プレイヤー跳び三への防御意識向上

**リスク**: 低（既存検証ロジックの最適化）

**優先度**: ⭐⭐ （中）

#### 4. **禁手脆弱性ペナルティの限界**

**現象**: 白の三延長点が禁手でも、黒は防御強要されて勝利につながらない場合がある。

**コード** (`forbiddenTactics.ts` の `evaluateForbiddenVulnerability()`):

```typescript
FORBIDDEN_VULNERABILITY_STRONG: 1000,  // 白攻撃ライン上
FORBIDDEN_VULNERABILITY_MILD: 400,     // 単独禁手
FORBIDDEN_VULNERABILITY_CAP: 2000,     // 最大 2000
```

**問題点**:

- ペナルティは「禁手が不利」を示唆するが、必ずしも有利につながらない
- 白が多方向から攻撃すれば、禁手ペナルティを補償できる
- ペナルティ上限 2000 は活三 2 個分だが、その実の価値は局面依存

**改善候補**:

- 白の複数ライン攻撃がある場合、ペナルティ減額
- または黒の禁手回避手に「後続カウンター脅威」があるかチェック
- `evaluatePosition()` で禁手ペナルティと攻撃脅威のトレードオフを厳密化

**期待効果**: 禁手局面での着手判定の信頼性向上

**コスト**: 中（既存ロジックの拡張）

**優先度**: ⭐ （低）

#### 5. **活二（OPEN_TWO）スコアと実際の価値の乖離**

**パターンスコア** (`patternScores.ts` L58):

```typescript
OPEN_TWO: 50,   // 活二
TWO: 10,        // 止め二
```

**問題点**:

- 活二は「将来的なパターンの素材」として評価されているが、連携度が高い活二は三発展に直結
- 例: 活二 4 個が同じ方向で連携 → 次手で複数の活三が作れる
- スコア 50 は活三 1000 の 5% だが、盤面制御度では活三並みの価値

**検出ロジック**:

- 活二検出は単純（`count === 2 && end1=empty && end2=empty`）
- しかし連携度を見ていない

**改善候補**:

- `evaluatePosition()` で多方向活二を検出時、連携度に基づいて加点
- または、活二が「活三ステップ」になる位置を事前判定

**期待効果**: 中盤の布局判定精度向上

**リスク**: 低（検出ロジック拡張）

**優先度**: ⭐ （低）

### Ⅱ. 探索アルゴリズムの問題（2 件）

#### 6. **水平線効果（Horizon Effect）による過剰なスコア膨張**

**現象**: Quiescence Search なしの場合、四+ブロックの短期的なやり取りで盤面スコアが膨張し、長期的な脅威判定を誤る。

**コード位置** (`quiescence.ts`, `minimaxCore.ts`):

**現状**:

- `quiescenceSearch()` は depth=0 で脅威手（四+ブロック）のやり取りを追加探索
- MAX_QUIESCENCE_DEPTH=4（四+ブロック 2 往復分）
- 「静止状態」に達したら `evaluateBoard()` で評価

**問題点**:

1. **Quiescence の制限が不十分**: depth 2 で深度不足により、複数の四が連鎖する場合を見逃す可能性
2. **四の防御点判定の簡潔性**: `getFourDefensePosition()` は「4 個連続 + 開き位置」のみで、複数防御点がある場合に不正確
3. **評価ベース値**: quiescence 後の `evaluateBoard()` が依然として末端評価ギャップを抱えている

**改善候補**:

- **A. Quiescence 深度拡張**: MAX_QUIESCENCE_DEPTH を 6-8 に引き上げ（コスト増加）
- **B. 防御点の複数検出**: VCF 同様に「すべての防御点候補」を列挙して評価
- **C. 「脅威がない状態」の定義厳密化**: 現在は脅威手がないだけだが、「互いに脅威がない」を要件に

**期待効果**: 四追いの評価が安定し、無理な四追いの判定精度が向上

**リスク**: 中（計算コスト増加、デバッグ困難）

**優先度**: ⭐⭐⭐ （高）

#### 7. **Null Move Pruning (NMP) と Late Move Reduction (LMR) の過剰枝刈り**

**現象**: hard 難易度で、相手の活三を見逃す。NMP で「有利すぎる局面」と誤判定される可能性。

**コード位置** (`minimaxCore.ts`, `techniques.ts`):

**NMP パラメータ** (`techniques.ts`):

```typescript
NMP_MIN_DEPTH: 3,
NMP_REDUCTION: 2,
```

**安全条件**:

- 相手に四（連続 4 個で片端以上開き）がない
- 連続適用しない（allowNullMove フラグ）
- 勝ち/負け確定スコアでない

**問題点**:

1. **「相手に四がない」の判定が甘い**: 活三（次手で四になる可能性）を見ていない
2. **depth 3 からの適用は早すぎる**: 序盤～中盤で過剰に枝刈りされる可能性
3. **複合脅威（活三×複数）の検出不足**: 単一方向の四チェックでは、複数方向脅威が漏れやすい

**LMR の問題**:

```typescript
LMR_MOVE_THRESHOLD: 3,  // 4 手目以降
LMR_MIN_DEPTH: 3,
LMR_REDUCTION: 1,
```

→ depth 3 で 4 手目以降の「有望でなさそう」な手を 1 深度浅く探索
→ **有望でない判断の根拠（Move Ordering スコア）が評価関数のバイアスに依存**

**改善候補**:

- **NMP 安全条件の強化**: 相手脅威検出を活三まで拡張
- **NMP 深度閾値引き上げ**: depth 4+ のみに制限（より深い探索でのみ)
- **LMR 除外条件の拡張**: 活三関連の手も LMR から除外
- または、手オーダリング精度向上により、「有望でない手」の判定を改善

**期待効果**: 相手脅威の見逃し減少、特に medium~hard での精度向上

**リスク**: 中（枝刈り効率の低下 → 探索時間増加）

**優先度**: ⭐⭐ （中）

### Ⅲ. 戦術探索の問題（2 件）

#### 8. **VCT カウンター脅威（ct=three, ct=four）の実装不完全**

**現象**: VCT 探索（終盤、stones >= 14）で相手のカウンター脅威を見落とし、偽陽性（実際には破れる VCT）を検出。

**コード位置** (`vct.ts` L195-199):

```typescript
// ct === 'three' || ct === 'four' の場合、
// 現在未実装、 hasVCF フォールバック等による検証が必要
```

**問題の構造** (`cpu-flow-review-plan.md` F-2, F-3):

**F-2**: VCT カウンター脅威が「四」の場合

- 黒が三を打つ → 白が四を作ってカウンター
- この場合、白の四で黒の VCT が破れる

**F-3**: VCT カウンター脅威が「三」の場合

- 黒が三を打つ → 白が三を作る（禁手なし）
- 白の三でも黒の勝ちが遅れるか不確定

**現在の対応** (`vct.ts`):

```typescript
const ctResult = await checkDefenseCounterThreat(board, lastDefense, attColor);
if (ctResult.threat) {
  const ct = ctResult.threat.type; // 'four' | 'three'
  // ... ct === 'four' と ct === 'three' を区別して処理する必要があるが未実装
}
```

**改善候補**:

- **ct=four**: 黒の三着手後、白の防御点で四が作れるか判定
  - → 作れれば VCT 破綻（黒は三を打つべきでない）
  - → 作れなければ黒が続行可能
- **ct=three**: 白の三防御でも黒が勝ち続けるか判定
  - → `findVCFSequence()` で「白の三防御後」でも VCF 成立か確認
- または、相手の三防御点に対して VCF を再探索

**期待効果**: VCT 検出の精度向上、終盤の勝負手の信頼性向上

**リスク**: 高（VCT ロジック全体への影響）

**優先度**: ⭐⭐ （中）

**既知の制限** (`cpu-ai-algorithm.md` L299):

- VCT 探索は hard のみ有効（難易度制限）
- 振り返りツールで使用（対局 CPU には未統合）

#### 9. **Mise-VCF 探索の「ノリ手」検証が不完全**

**現象**: ミセ手（四三狙い）→ 相手防御 → VCF という手順を検出するが、相手が「ノリ手」（三防御）で破綻させる可能性を過小評価。

**コード位置** (`miseVcf.ts` L61-90):

```typescript
function isInvalidatedByNoriTe(
  board: BoardState,
  color: "black" | "white",
  threeDefenses: Position[],
  ...
): boolean | null {
  // 相手の三防御位置ごとに hasVCF / findVCFSequence を再実行
  // → ただし「部分的」な検証のみ（全シーケンス追跡なし）
}
```

**問題点**:

1. **三防御検出の不完全性**: ミセ手が「活三 + 四三点」を同時に作った場合、三防御候補が複数あるが、すべてを列挙しているか不確定
2. **VCF 再検証の範囲**: 相手が三防御した「その局面からの」VCF を検証しているが、その後のVCTは未考慮
3. **タイムアウト処理**: `isInvalidatedByNoriTe()` で時間制限超過時は `null` を返し、「無効化されたかどうか不明」のまま先に進む可能性

**改善候補**:

- `findMiseTargetsLite()` で三防御候補をさらに確実に列挙
- 三防御後の VCF 再検証で、単なる「VCF 成立」だけでなく、「元々のミセ手フローと異なる展開」をトレース
- またはミセ手自体の事前判定を厳密化（相手の「有力な防御」を先読み）

**期待効果**: Mise-VCF の偽陽性減少、終盤の着手信頼性向上

**リスク**: 低～中（既存ロジック拡張）

**優先度**: ⭐ （低）

### Ⅳ. アーキテクチャ上の問題（2 件）

#### 10. **detectOpponentThreats() の二重呼び出し（R-1）**

**現象**: 計算の冗長性により、無駄な脅威検出処理が 2 回実行される。

**コード位置** (`iterativeDeepening.ts` L126, L392):

```typescript
// 1回目: L126 (findPreSearchMove 内)
const opponentThreats = detectOpponentThreats(board, opponentColor);

// 2回目: L392 (候補手制限ロジック)
const threats = detectOpponentThreats(board, opponentColor);
```

**問題点**:

- 同じ盤面の脅威検出が 2 回走る
- `detectOpponentThreats()` は全盤面走査のため計算量が多い
- キャッシング機構がない

**改善案** (`cpu-flow-review-plan.md` Phase-3):

- 最初の呼び出し結果をキャッシュ
- 2 回目は キャッシュ結果を参照

**期待効果**: 探索時間 3-5% 短縮

**コスト**: 低（既存キャッシング機構の活用）

**優先度**: ⭐ （低、速度改善）

#### 11. **候補手制限ロジックの分散（R-2）**

**現象**: VCF 防御セットと活三防御セットの生成ロジックが 2 箇所に分散。

**コード位置** (`iterativeDeepening.ts` L248-284, L390-407):

```typescript
// ブロック1: findPreSearchMove 内
const restrictedMoves = [
  ...vcfDefenses,
  ...openThreeDefenses,
];

// ブロック2: 候補手生成ロジック
const restricted = detectOpponentThreats(...);
const defensePositions = [...];
```

**問題点**:

- ロジックの重複により保守性低下
- 変更時に両箇所の更新が必要

**改善案** (`cpu-flow-review-plan.md` Phase-4):

- 候補手制限を統一された Phase に集約
- `findPreSearchMove()` の責務を明確化（即時手の検出のみ）

**期待効果**: コード可読性向上、バグ減少

**優先度**: ⭐ （低、リファクタリング）

## 推奨実装順序

### Phase A（即座に着手可能な改善、実装リスク低）

1. **末端評価ギャップ対策** (1)
   - `evaluateBoard()` に `isMiseMove()` 同等の判定を統合
   - `--score-override` で LEAF_FOUR_THREE_THREAT を段階調整可能
   - ベンチマークテストで効果定量化

2. **detectOpponentThreats 二重呼び出し排除** (10)
   - キャッシング実装（3-5% 高速化）
   - 低リスク、即実装可

### Phase B（中程度の複雑さ、実装前のレビュー推奨）

3. **NMP/LMR の安全条件強化** (7)
   - 脅威検出を活三まで拡張
   - depth 閾値見直し
   - ベンチマークで相手脅威見逃し率測定

4. **跳び三防御ロジック最適化** (3)
   - 制約ライン検証の簡略化
   - 禁手回避時の三有効性判定改善

### Phase C（高リスク、設計検討が必要）

5. **水平線効果対策** (6)
   - Quiescence 深度拡張検討
   - 防御点複数検出実装
   - 詳細なプロファイリングが必須

6. **VCT カウンター脅威実装** (8)
   - ct=four, ct=three 分岐の実装
   - 振り返りツール側の VCT 検証も同時実施
