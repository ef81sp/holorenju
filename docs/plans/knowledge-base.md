# 知識ベースによるCPU性能向上

## 背景

### スコア体系改善の結果（Phase 2-3）

パターンスコアの微調整とmove ordering変更は、統計的に有意な改善をもたらさなかった。

| テスト          | 局数 | Elo             | 結論         |
| --------------- | ---- | --------------- | ------------ |
| THREE=100       | 100  | +17.4 [-50, 86] | ノイズの範囲 |
| THREE=150       | 200  | 0 [-48, 48]     | 完全互角     |
| フクミ手 on/off | 200  | -10.4 [-59, 38] | 効果なし     |

### なぜ効かなかったか

- 深度4の探索は既に三/四の脅威を「見えている」
- パターンスコアはmove orderingに影響するが、全候補手を結局探索するため差が出ない
- **ボトルネックはスコアの精度ではなく分岐数**

### 知識ベースが効く理由

知識（定石、形の良し悪し、必勝パターン）を導入することで:

1. **候補手の絞り込み** — 「検討する価値がない手」を知識で除外 → 分岐数削減
2. **move ordering改善** — 知識で最善手の予測精度が上がる → alpha-beta枝刈り率向上
3. **探索の省略** — 定石や既知パターンでは探索自体をスキップ

これらにより同じ時間でより深く探索でき、結果的にCPU強度が上がる。

## 提案: 4つのアプローチ（優先度順）

### 1. 定石データベース（最優先）

**概要:** 連珠の序盤定石（珠型ごとの最善手順）をデータ化し、序盤の探索をスキップする。

**連珠の珠型体系:**

連珠では先手（黒）の3手目の位置で珠型が決まる（26種）。各珠型に対して白の応手、さらに黒の5手目…と定石が体系化されている。

- 直打ち（13種）: 瑞星、山月、丘月、渓月、寒星、花月、雨月、松月、残月、新月、明星、金星、天元
- 斜打ち（13種）: 長星、峡月、恒星、水月、流星、雲月、浦月、嵐月、銀月、名月、彗星、遊星、慧星

**CPUでの利用:**

- 現在の局面が定石手順にマッチするか判定
- マッチすれば定石の次の手を即座に返す（探索スキップ）
- 序盤の10秒×数手を節約 → 中盤以降に時間配分

**シナリオでの流用:**

- 定石データに解説テキストや分岐情報を付加すれば、シナリオの「デモモード」で定石解説に使える
- 「問題モード」で定石の分岐点を出題することも可能
- データ形式を工夫してCPU用とシナリオ用の両方で使えるようにする

**データ形式のイメージ:**

```typescript
interface JosekiNode {
  // 棋譜上の手（座標）
  move: string; // e.g. "H8"
  // この手の評価（CPU用）
  evaluation?: "best" | "good" | "playable" | "bad";
  // 解説（シナリオ用、省略可）
  comment?: string;
  // 分岐
  children: JosekiNode[];
}

interface JosekiBook {
  // 珠型名
  name: string; // e.g. "花月"
  // ルートからの手順
  root: JosekiNode;
}
```

**データソースの課題:**

- 連珠の定石データを体系的にまとめた機械可読なソースが必要
- 選択肢:
  - 既存の定石データベース（RIF、連珠世界の棋譜集等）から変換
  - 手動で主要珠型の定石をエンコーpsド
  - 強いエンジンの自己対戦から生成
- 最初は主要5-10珠型の基本定石から始め、段階的に拡充

**実装の影響範囲:**

- 新規: 定石データファイル、定石マッチングロジック
- 変更: `iterativeDeepening.ts`（定石ヒットで早期リターン）
- シナリオ連携は定石データが安定してから別フェーズで

### 2. 形の知識（候補手pruning）

**概要:** 局所的な石の配置パターン（形）に基づいて、候補手の質を事前判定し、明らかに悪い手を探索対象から除外する。

**具体例:**

- **孤立手の除外**: 既存の石と全く連携しない位置（周囲に自分の石がない）
- **死に形の延長**: 既に両端が塞がれた二の延長は無価値
- **急所認識**: 特定の形における急所（ここに打たないと負ける/ここに打てば勝つ）
- **筋の良し悪し**: 経験的に「筋が良い」とされる形（斜めの連携、中央志向等）

**現状との差分:**

- 現在の `generateSortedMoves` は位置ベースのフィルタリング（脅威近傍の候補生成）
- `evaluatePositionCore` はパターンマッチで二/三/四を検出
- 不足: 「この形は将来性がない」「この手は筋が悪い」という質的判断

**期待効果:**

- 候補手数を30→15程度に削減できれば、同じ時間で1-2手深く読める
- alpha-beta の理論的な枝刈り効率は `O(b^(d/2))` なので、b（分岐数）の削減は劇的

**実装の影響範囲:**

- 新規: 形パターン辞書、パターンマッチングロジック
- 変更: `generateSortedMoves` のフィルタリング強化、または `evaluatePositionCore` のスコア改善

### 3. キラーシェイプ（必勝/必敗パターン辞書）

**概要:** 「この局所パターンが成立したら必勝/必敗」という既知の形をハードコードし、探索中にパターンマッチで検出したら即座に評価を確定する。

**具体例:**

- 四三が同時に作れる形（現在は `FOUR_THREE_BONUS` で部分カバー）
- 複数方向の三が連携して止められない形
- 禁手に追い込まれる形（黒番）

**現状との差分:**

- 現在のVCF/VCT事前チェックは手順ベースの探索
- キラーシェイプはパターンマッチベースの即座判定 → 高速

**期待効果:**

- 探索木の枝を早期に刈り取れる
- VCF/VCTと補完的（VCFは手順探索で正確だが遅い、パターンは即座だが限定的）

**実装の影響範囲:**

- 新規: パターン辞書
- 変更: `evaluatePositionCore` or minimax内部での早期打ち切り

### 4. 脅威空間探索 (TSS)

**概要:** VCF（四追い）/ VCT（三四連続勝ち）を一般化した探索フレームワーク。脅威（三、四）のみに着目した専用の探索木を構築する。

**現状:**

- VCF: 実装済み、事前チェックで使用
- VCT: 実装済みだが hardのみ、ヒント手として使用
- これらは個別実装で、統一的なフレームワークがない

**TSSの利点:**

- 通常のminimax探索とは独立した脅威専用探索
- 脅威手のみを探索するため分岐数が小さく、深く読める
- 必勝手順の発見精度が向上

**リスク:**

- 実装コストが大きい（VCF/VCTの根本的な書き換えになる可能性）
- 現在のVCF/VCTが既にそこそこ機能している
- `vct.ts` が2120行と巨大で、改修の前にリファクタリングが必要

## 検証方法

各アプローチとも `ab-bench` の `--sprt` で効果検証する。

1. 定石DB: 定石あり vs なしで対局（序盤の手の質 + 中盤の時間配分効果）
2. 形の知識: 候補手pruningあり vs なしで対局
3. キラーシェイプ: パターン判定あり vs なしで対局
4. TSS: 新TSS vs 現行VCF/VCTで対局

## 前提条件

- **リファクタリング先行**: テストの不安定性解消と大ファイル分割を先に行う
- 特に `vct.ts`（2120行）は分割必須
- テスト実行時間の改善も必要（現在全テスト約145秒）

## 次のステップ

1. リファクタリング計画を別途策定・実行
2. 定石データのソース調査（機械可読な連珠定石データの入手方法）
3. データ形式の設計（CPU用 + シナリオ用の両立）
4. 主要珠型の定石エンコード（5珠型程度から開始）
5. `iterativeDeepening.ts` への定石マッチング組み込み
6. ab-bench で効果検証
