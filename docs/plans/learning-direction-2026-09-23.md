CPU 強化は 2026-09-22 に打ち止め（main 0eff585、V1c＋quiescence 受け強制まで）。以後は「強くなったエンジンの仕組みを、いかに学習につなげるか」を設計する。本メモは方向決めのための棚卸しと提案で、実装プランは方向が決まってから別メモに書く。

### 1.1 指導対局モードが最大の未回収資産

設計書（`docs/coach-mode/00-overview.md`）の要点: CPU 対局中、着手直後に裏で評価し、最善以外なら「ここに打つ手があった」と提示して**打ち直し**を選ばせる。Phase 5 では敗勢を伝えて**敗着の手番まで巻き戻す**。解説は探索結果（四追い・追い詰め・両ミセ・受け）と prospect 評価の内訳から生成し、後付けの特徴抽出をしない。2026-07-25 と 08-02 の実プレイ検証で 19 件を修正済み。

つまり「自分のミスをその場で打ち直して学ぶ」は既に作ってある。振り返りから問題を作る案（前回提案の 1）は、指導対局の打ち直し・巻き戻しとほぼ同じ体験になる。**新しく作る前に、これを development に取り込むのが先**。

未マージの理由は記録にない（8 月以降は強さの作業に専念していた）。取り込みの技術的な障害:

- 衝突は `src/logic/cpu/review/forcedWinDetection.ts`（development 側は #104/#119/#122 で VCT の歯止めと詰み木の変更）と `zig/src/main.zig`（coach 側は prospect 内訳の export 72 行を追加、development 側は stats／qtrace の export を追加）。どちらも局所的。
- coach の評価は `review.worker` の fullEval を流用しているので、8 月以降の探索変更（VCT 取りこぼし修正・V1c・受け強制・exact_top_k）はそのまま効く。ただし**評価値のスケールが受け強制で圧縮された**ので、coach が使う点差しきい値（振り返りと同じ 150/400/2500）と「good 域は介入しない」の境界は、§12.9 の再較正で据え置きになったとはいえ、介入頻度を実プレイで再確認する必要がある。

## 3. 提案

**A → E → D の順**。理由:

1. A は 9,000 行の実装と 2 回の実プレイ検証が済んでいて、取り込みだけで学習体験が一段変わる。放置するほど development から離れて取り込みコストが上がる。
2. D は coach の解説生成（`coachExplanation.ts`、`coachDialogues.ts`）を振り返り側に流用できるので、A の後なら安い。振り返りの定型文（`QUALITY_DIALOGUES`）を、四追い・追い詰め・受けの手順つきの説明に置き換える。
3. B は A の巻き戻しと重なる。A を使ってみて「対局後にも反復したい」となったら着手する。
4. C は独立しているが、問題モードの判定拡張（`sequence`・VCT）が先に要る。A〜D の後、または並行で別途。

### 3.1 A の進め方（案）

1. `feat/coach-mode` を development の上に rebase せず、**development を coach にマージ**して衝突 2 件を解決する（45 コミットの rebase は衝突が連鎖しやすい）。マージ後に `pnpm check-fix`・全テスト・wasm テスト。
2. 実プレイ再検証（Chrome DevTools MCP、`reference_holorenju_browser_playtest`）: 介入頻度・打ち直し・巻き戻し・評価待ち時間。受け強制でスケールが変わった影響を見る。
3. Opus 3 観点レビュー → PR（development 向け）→ マージはボス判断。

## 4. ボスに決めてほしいこと

- 指導対局モードを取り込む方針でよいか。未マージのまま止まっていた理由（機能面の不満・未完成の認識など）があれば教えてほしい。
- A の後の優先順位（提案は E → D → B/C の順）。
