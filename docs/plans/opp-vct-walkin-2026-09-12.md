## 0. 結論（先出し）

1. **「根で相手の追い詰めをプローブする」案は上積みなし**。A 22 件すべてで、実際に指された白の手が根の追い詰めを解消していた（lenient 深さ 8・100 万ノードでも残らない）。根の score が追い詰めを反映していなくても着手は正しかった。→ 撤回。
2. 本物の穴は **1 手先**にある。B / B-deep 73 件（準備局面で勝者に追い詰めが成立）の敗者の根で hard を再探索すると、**最善手の後に相手の追い詰め（lenient 深さ 5・20 万ノード）が残るものが 39/73**。そのうち探索が損を見えていない（root score > −1500）ものが **17 件**、上位 5 候補に安全な代替手があるものが **12 件**（うち 10 件は第 2 候補）。
3. 見えない理由は 2 つで、**予算の方が大きい**（39 件で数えた「1 手後の局面で追い詰めが見つかる件数」、深さ 4）:

   | モード \ ノード | 3k（現行プローブ） | 10k | 25k | 100k |
   | --------------- | -----------------: | --: | --: | ---: |
   | strict（現行）  |              **4** |   6 |  13 |   17 |
   | lenient         |                 10 |  13 |  21 |   32 |
   - 現行の防御ノード用プローブ（strict・3k）は 4/39 しか見ない。探索が損を見ていない 17 件では 0/17。
   - strict の「ノリ手ゲート」（相手の四のブロックが四でなければ手順崩壊とみなす、`vct.zig` `hasBreakingCounterFour`）は 17 件中 11 件を予算無制限でも棄却する。その 11 件のうち 7 件は勝者の探索が 99980（詰み確定）で反転している＝本物の負け筋を「幻」として捨てている。ゲートの精度（棄却のうち幻の割合）は最大 4/11。

4. 提案するレバーは 2 本（独立にスクリーニングできる）:
   - **S-L**: 防御ノードのプローブを strict → lenient（モジュール変数 `defensive_probe_mode` の既定値）。安いので先に固定スクリーン（2026-09-13 起動、§10）。
   - **V1**: 反復深化後に**最善手 1 手だけ**「置いた後に相手の追い詰めがあるか」を lenient・大予算で検証し、見つかれば上位 3 候補のうち安全な最上位に切り替える（`demotePlainFourIfNeeded` と同じ後処理の型）。予算は主探索から**予約**し、両モードの総仕事量を変えない。

5. 期待効果の上限（パフォーマンス観点の見積り）: 穴 17 件は plycheck v2 の 809 開局 × 4 手 ≈ 3,200 局面の 0.5%。100k で検出 15/17、安全な代替あり 12/17、上位 3 内 ≈ 9 件 → 実際に切り替わるのは局面の約 0.25%、1 局 30 手で **1 局の約 7% に 1 回**。全部が負け→非負けでも **+10〜20 Elo 級**。#163（+27.6）並みは期待しない。固定前半 382 局では保留域（点推定 ≥ +10 で CI が 0 を含む）に落ちる可能性が高いので、**保留なら後半を待たず時間モード 1,200 局で直接追試**（strength-screen §6.18 教訓 3）。

## 3. 原因の構造

1. **予算**: 主探索の防御ノード（相手手番）で走るプローブは VCT 3k（時間 25 ms）。#163 で 6k→3k にして +27.6 を得たとおり、**全ノードで走るプローブの上限は小さいほど良い**（20k で −60）。だが 1 手先（根の子）で長さ 7〜13 の追い詰めを見るには 25k〜100k 要る。全ノードで払えない予算は、**根の最善手 1 件にだけ**払う。
2. **モード**: strict のノリ手ゲート（dca749c、`vct-fp-asymmetric-2026-06-10.md`）は「相手に四が 1 本でもあり、そのブロックが四を作らなければ崩壊」と見なす。lenient は同じ場合に `checkSequenceBreaksByCF`（CF＋ブロックを置いた盤で残り手順が成立するか）まで見る。dca749c の「防御側の過剰棄却は低リスク（本当に被詰みなら受けは無い）」という前提は、**受けがある 1 手前**（本メモの 17 件）では成り立たない。過剰棄却が自ら追い詰めに入る手を許している。
   - dca749c 当時の Elo 検証結果は記録されていない（approach A の −88.7 は攻め側を締めた別案）。randomFactor 無効時代（[[project_bench_randomfactor_noop]]）なので当時の判断は現ベンチで再測が要る。
   - dca749c の幻は**実コーパスの中盤局面**で起きた。計測 1〜3 はすべて 7〜11 石の序盤帯（対照群平均 8.0 石）で、逆四が稀なため strict の棄却が本物に偏り、lenient の偽陽性が低く出ている可能性がある。→ §9 の実戦棋譜走査で中盤を測る。

## 4. レバー S-L: 防御ノードのプローブを lenient に

- 変更（ブランチ `screen/probe-lenient` f7b085f）: `minimax.zig` に `pub var defensive_probe_mode: vct_mod.ResilienceMode = .lenient;` を置き、`threatProbe` は `if (defensive) defensive_probe_mode else .lenient`。攻めノードは不変。採用時は既定値の変更で済み、同一 wasm で A/B も可能。
- 期待: 上表の 4 → 10（3k）。副作用 2 つ: (a) 幻の被詰み（dca749c の再現局面 G8 / −8864 → −99999）が戻り受け身手を選ぶ、(b) strict はノリ手ゲートで早期棄却するので lenient はプローブが高くつく（#163 の逆方向）。
- 判定は Elo 一本にしない。副指標: プローブ上限到達率・平均深さ（コストの分離）、**幻の被詰み回帰セット**（dca749c の再現局面 + §9 の走査で「lenient は追い詰めあり・strict はなし・指した側が負けていない」局面から数十件）で着手が変わった件数。
- 既知: `reviewExactTopK.wasm.test.ts` (d)「同値の 2 位以下が exactTopK=5 で分かれる」は特定局面の探索結果に依存する性質テストで、S-L で分かれなくなり落ちる（screen コミットはフック省略）。採用時は別局面に差し替える。Zig テスト 4,142 本・golden は緑（期待値不変）。
- 第 3 案 **S-G（strict ゲートの緩和）**: 棄却 11 件（本物 7）を材料に「ブロックが四でない」に加える条件（例: ブロックで相手に活三／ミセ／VCF が生じる場合だけ崩壊）を定義できる可能性がある。S-L の結果を見てから着手する（S-L が負なら S-G、正なら不要）。

## 5. レバー V1: 根の最善手の「自ら追い詰めに入る」検証

### 5.1 位置と責務

- `search.zig` `findBestMoveIterative` 末尾の後処理。`demotePlainFourIfNeeded` と共通部（仮置き＋bitboard 同期→`analyzeFourAndThree`→復元＝`isPlainFourMove`、`switchToCandidate`）を抽出し、demote と V1 を同一セクション（または `root_postprocess.zig`）に寄せる。`findVCTMoveWithLimiter` は内部で `bitboard.initFromCells` を呼ぶので、候補を戻したあと `bitboard.removeStone` で同期する（demote と同じ）。
- 事前探索の即決手（`immediate_move`）と唯一手の早期 return 経路には入れない。振り返り経路（aspiration_mode≠0）も demote と同様に通る（§5.6-6 で判定一致を確認）。
- **`finalizeStats(&ctx)` を後処理の後ろへ移す**（現状は demote の前に `final_result.stats` へコピーされる）。V1 の消費・skip はここで畳む。

### 5.2 予算（予約方式）

- **時間モード**: 主探索の `ctx.deadline` を `dynamic_time_limit − WALKIN_TIME_RESERVE` で立て、V1 は `TimeLimiter.untilDeadline(absolute_deadline).child(WALKIN_TIME_RESERVE, 0)` を親にする。hard は主探索が 10 s に張り付く手が 22〜24% あり、「絶対デッドラインとの min」だけでは**緊迫局面ほど V1 が走らない**。予約なら 1 手の合計時間は不変。
- **決定的モード**: 主探索 `max_nodes = N − WALKIN_NODES_RESERVE`、V1 の親予算 `WALKIN_NODES_RESERVE`。消費は `stats.nodes` に計上（事前探索・プローブと同じ規約）。**変種が追加予算を得ない**（N スイープでは +8% ≈ +5 Elo、+25% ≈ +15 Elo の交絡があり、期待効果と同じ桁）。demote の VCF（3k、非計上）は据え置き、差は明記。
- 親予算を K 回の検証で共有（子は親の残り全部）。「見つかった」は早く終わる（穴 17 件で p50 73〜98 ms）ので、代替候補の検証にも通常は予算が残る。最悪でも合計は予約額で頭打ち。
- 初期値: `WALKIN_NODES_RESERVE = 100_000`（1.2M の 8%）、`WALKIN_TIME_RESERVE = 400` ms（無負荷 100k「なし」p50 276 ms、jobs=5 負荷下は約 3 倍。時間側が固定側より弱いと固定で出た効果が時間ゲートで消える）。**P1 と同じ規則で較正**: ベンチ JSON の V1 `tripped` 率を両モードで一致させ、時間側を動かすか固定側を 50k に下げるかを到達率で決める。
- 定数は時間定数の隣（`search.zig`）、`BudgetPolicy.walkin_nodes`（TIME_MODE は 0、DETERMINISTIC は search 定数参照、`derive` テストに `> 0` を追加）。

### 5.3 手続き（margin なし）

```
if top_candidate_count < 2: return
if |result.score| >= WINNING_SCORE_THRESHOLD(2500): return   // 勝ち筋・負け確定は触らない
parent = 予約予算
checks = 0
置く(best); found = findVCTMoveWithLimiter(opponent, VCT_MAX_DEPTH=5, parent.child(残り全部), .lenient); 戻す; checks++
if parent が空で未判定: stats.walkin_skipped++; return
if !found: return                                   // 大半の手
for c in top_candidates[1..]:                       // 順位順、最大 WALKIN_MAX_CHECKS(3) 回まで
    if checks >= 3 or parent.exhausted(): break
    if isPlainFourMove(c): continue
    置く(c); ok = !findVCTMoveWithLimiter(opponent, ..., .lenient); 戻す; checks++
    if ok: switchToCandidate(result, c); stats.walkin_switches++; return
// 全候補が追い詰めに入る／予算切れ → 最善手のまま
```

- **margin は置かない**。製品経路の候補 score は bound（§2）で機能しないため、lenient 偽陽性の損失は**実戦介入率（§9）と screen** で縛る（§9.2 で偽陽性 0.4% を確認済み）。

#### 5.3a v3: 代替は「最善手を除外した根の再探索」で得る（V1c）

実装中に判明（2026-09-13）: 製品経路（exact_top_k=0）の第 2 候補以降は aspiration 窓の外で最初に切られた手が bound 順に並ぶだけで、真の第 2 候補ではない。局面 1（§5.6-1）は決定的 hard で候補 2〜5 が全部 −361 の同点かつ全部 walk-in、I6/J7/K8 は上位 5 に入らず、上記の候補ループでは切り替わらない（exact_top_k=5 なら F9 → I6 に切り替わる）。§2・§9.2 の「上位 3 に安全な代替 12/44」は exact_top_k=5 の真値順で測った数字であり、bound 順では再現しない。

→ 候補ループを廃止し、発火時（最善手が walk-in）は**最善手を除外集合に入れて根を反復深化で再探索**（深さ 2〜completed_depth−1、予算内で完了した最後の深さ）し、その最善手を VCT で検証、walk-in なら除外に加えて繰り返す（最大 `WALKIN_MAX_CHECKS = 3` 回）。根探索に除外集合（`SearchContext` の除外リスト、根の手ループでスキップ）を追加する。

予算（v3）:

- 決定的モード: VCT 検証は `WALKIN_NODES_RESERVE`（100k、主探索 N から予約、§5.2 のまま）。再探索は**発火時のみ**の追加予算 `WALKIN_RESEARCH_NODES = 150_000`／回で、`stats.nodes` と `walkin_nodes` に計上。発火は手の約 9%（§9.1）なので平均の追加は +1〜2% ≈ +1 Elo 未満の交絡（主探索からは予約しない。予約すると全手が 17% 浅くなり −10 Elo 級の税になる）。
- 時間モード: VCT 検証は `WALKIN_TIME_RESERVE`（400 ms、予約）。再探索は絶対デッドラインまでの残りと `WALKIN_RESEARCH_TIME = 1,000` ms の min。残り 100 ms 未満なら再探索せず `walkin_skipped`。10 s 張り付きの手（22〜24%）では再探索が走らないことを skip 率で観測し、時間ゲートで判定する。
- 二段判定（lenient で発見→strict で再検証し margin を階層化）は、strict が本物を 11/17 落とすため採らない。
- 相手の追い詰め探索は `findVCTSequenceInner` の仕様上、自分の最善手が活三を作る場合は VCF-only に落ちる（「四で活三を潰してから三で追う」相手の手順は見えない）。取りこぼし側の限界として明記。

### 5.4 統計・可観測性（append-only）

- `SearchStats` 末尾に `walkin_checks` / `walkin_switches` / `walkin_skipped` / `walkin_nodes` を追加し、stats_buffer は **append-only**（+68/+72/+76/+80、`STATS_FIELD_COUNT` 20、TS は `getStatsBufferLength() >= 84` で判定、`scripts/lib/wasmSearchStats.ts` の optional フィールド）。独立 export や features 新ビットは使わない（存在判定の SSoT を二重化しない。`budget.zig` の `searchFeatures` テストは値 3 固定）。
- commit-bench の `moveHistory[].stats` に載せ、screen の副指標: 介入率（switches／手）、skip 率（時間モード）、`tripped` 率（較正）、`walkin_nodes` の平均・最大。

### 5.5 やらないこと

- 根の全候補（20〜40 手）の検証。上位 3 手に限る。
- 深さ 1 の子ノードでプローブ予算を上げる（子は 20〜40 あり合計が主探索を食う。#163 の逆行）。
- 「相手の脅威手が 0 なら省略」ゲート: 対照群で 30% 発火するがその局面は元々ほぼ 0 ms で得が無く、穴 73 局面では 0% 発火。尾の制御はノード上限で足りる。

### 5.6 テスト（TDD、決定的モードで書く）

ネイティブテストは時計が 0 で時間予算が無制限になるため、`budget_mod.deterministic_mode = true; defer … = false;` で書く。時間モードは「予約で deadline が縮む」「予算切れで skip が数える」の分岐だけ確認。

### 10.6 実装レビュー（3 観点、Opus、2026-09-13）と対応

3 観点とも要修正。指摘を「hard の対局経路の挙動を変えない修正（PR に入れる）」と「探索挙動が変わる改良（再ベンチが要る follow-up）」に分けた。

PR に入れる（採用済みの時間ゲート結果を無効にしない範囲）:

1. 適用範囲のゲート: `params.max_depth < 3`（beginner / easy）は予約も検証もしない（切り替えは原理的に起きないのに主探索の 20% を失っていた）。`completed_depth < 3` の判定を最初の検証より前へ。
2. 振り返り経路（aspiration_mode≠0 / exact_top_k>0）では走らせない: 切り替えで `result.position/score` と `top_candidates`/`exact_mask` の整合が壊れ、`fullEval.ts` の `playedIsBest` / `resolvePlayedScore` が「穴に入った手を最善」と判定し得る。除外再探索の TT 上書きが候補 PV にも影響する。振り返りの 14/14 一致は経験的証拠であり不変条件違反は残っていた。
3. 小予算の決定的モード（`max_nodes ≤ 予約額`）は検証を走らせない（主探索 50k に対して検証 100k が走り N スイープの較正を壊す）。

## 12. quiescence の診断（設計、2026-09-14）

### 12.1 目的

§11.9 の「静的評価は Rapfi の手を上に置くのに深さ 1（子の quiescence）で覆る」局面で、quiescence が何をしているかを観測し、機序を特定する。quiescence（`zig/src/quiescence.zig`）は四を作る手と強制受けだけを最大 4 段辿り、stand-pat（`last_mover_is_perspective` で手番を補正した静的評価）と比較する。候補となる機序:

1. **四の応酬後の静的評価の落ち込み**: Rapfi の手（四を作る）→ 強制受け → 局面の四が「止まった四」になり、prospect 基底の脅威カテゴリが消えて評価が下がる（Rapfi は受けを強いたテンポ・形を評価している）。
2. **相手のカウンター四**: 受けの後に相手が四を作れる手を quiescence が拾い、我々の側の評価が下がる（本来は相手の四も受ければ済む）。
3. **stand-pat の手番補正の非対称**: 深さ 0 の子は相手手番なので `last_mover_is_perspective = .yes`。根の静的評価との差（horizon-flips メモ「静的評価は手番側に悲観的」中央値 854）が候補間で非一様に効く。
4. **TT の再利用**: quiescence は TT を負の深さで共有する。主探索の別経路の値が混ざる。

### 12.2 観測 API（実装）

- `zig/src/quiescence.zig`: 診断用のトレース（`pub var q_trace_enabled: bool`、`QTrace{ standpat_root, value, pv: [MAX_QUIESCENCE_DEPTH]Position, pv_len, standpats: [..]i32, cut_reason }`）。`quiescenceSearch` の各ノードで best 子の手と stand-pat を記録（有効時のみ。無効時のホットパスは分岐 1 つ）。TT は診断時に無効化（`q_trace_enabled` なら probe/store を飛ばす）して純粋な木の値を見る。
- `zig/src/main.zig`: `export fn quiescenceTraceWasm(color, last_row, last_col)`（盤面は既存の board バッファ、eval は hard の EvalOptions）→ 結果バッファ（value, standpat, pv_len, pv 座標列, standpats）。
