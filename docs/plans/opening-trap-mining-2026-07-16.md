# 序盤トラップ採掘プラン（opening trap mining）v2

## ★実行結果（2026-07-16、run1）— 判定: **ブック化に進む（閾値 5 を大幅超過）**

- 実行: 34ルート × b5=12 × b7=20 → **6,407 チェック**（実機 hard 10s・6並列・約4.5h）
- **severity-A: 43 canonical 局面（49 レコード）**、全件実機再検証済み。
  VCF 29 / VCT 20。22/34 ルートに分布（水月8・名月6・明星/渓月/丘月各3など、集中せず広範）
- サニティ検証: 手順長1〜3の短い勝ちは「達四（受けなし）」の正しい判定
  （sequence は最後の五を含まない仕様）。チェッカーのバグではない
- **帰属分類**: 白8回避可能（真の白8敗着、代替に生存手 2〜5 あり）= **42/43**。
  ply7全滅（それ以前に敗着）= 1/43（**彗星** `H8 I9 F6 J8 F8 J9 E8`、白の候補全てに
  黒の 11手 VCT。個別調査の価値あり）
- 解釈: 序盤の受けは体系的崩壊ではなく「白8 の選択がピンポイントに悪い」局所敗着が
  広範囲に散在する構造。42件が「生存手が既に判明している」ため、**ブック（正しい手の
  焼き込み + 同格手ランダム化）が最も直接的な対策**。eval 再調整でのモグラ叩きは不適
- 結果: `bench-results/opening-traps-run1.jsonl`（gitignore。消えたら再実行 ~4.5h）

## 0. 位置づけ

- **目的**: 序盤（〜8手目）で「人間の打ち回しに対して hard の応手が相手の強制勝ち
  （VCF∪VCT）を許す」局面＝**トラップ**を機械的に発見し、密度を実測する。
- 成果:
  1. **トラップ密度の実測** — 序盤定石ブックへの投資判断の根拠（事前登録基準は §6）
  2. `scripts/regression-positions.ts` レジストリの**自動拡充候補**
  3. 副産物: 序盤コーパス増強素材・プレイヤー向け問題モードの素材候補
- 性格: **存在証明のための調査**。偽陰性（取りこぼし）は許容、偽陽性（誤トラップ認定）は
  実機再検証（§4）で排除する。

## 1. ステップ0: 無料の事前分布（issue レビュー提案）

本実行の前に、既存 commit-bench 棋譜（3,848局 + 直近の r2 ベンチ 416局）を走査し
「20手以内の早期決着局のうち、敗者側の 8手目以前の手に敗着（その手の直後から
勝者に強制勝ちが成立）があった局」を数える。ほぼ無料（保存済み棋譜の再解析）で
序盤トラップ密度の事前分布が得られ、本実行の規模調整（§5）にも使う。

## 2. 設計の核心: 「両側 top-K」ではなく「攻め側=広く、hard 側=実機」

- **J6 事例の教訓**: 攻め側（人間）の布石（I7、そして5手目 H7 も）は minimax 順位が
  低くても罠を張れる。両側 top-K 列挙ではこの種の線を発見できない。
- 防御側（hard）は randomFactor=0 で決定的なので分岐は1本 = 実機
  `findBestMove(board, color, "hard")`。
- **攻め側のフィルタは黒5・黒7とも同一の思想で構成**（v1 は黒5が top-K 偏重で
  §2 の思想と矛盾していた — issue レビュー blocker 反映）:
  - 脅威プレフィルタ: その手で自分の石2つ以上と「二（2方向以上）」を構成する手
  - ＋ 候補スコア上位（親局面の `findBestMoveForReview` の candidates 順位 — 1親1回で
    全子手のランクが得られる）
  - ＋ ランダム枠（シード固定）
  - **検証済み**: ボス実戦の黒5=H7（H8と縦二 + I8と斜め二 = 2方向）・黒7=I7 は
    脅威プレフィルタを通る想定。E2E テスト（§7）で機械的に固定する。

## 3. ルート集合（issue レビュー blocker 反映）

- 人間=黒の第1段。黒1=天元（ルール）、白2=CPU の実機挙動（間接/直接の両クラスを
  カバー）、**黒3=自由**。
- ルート = 26珠型（黒3が天元5×5箱内の全カノニカル形をカバー。**ボス実戦の
  H8-I9-I8 は「雲月」に一致することを確認済み**）＋ **珠型外ルート**（黒3が
  白2の周囲2マス内だが天元から距離3以上のセル。対称正規化後 数個〜十数個）。
- 人間=白（攻め手番3つ）は第2段。第1段の密度・歩留まりを見てから設計。

## 4. パイプライン

```
ルート（3手・§3） → hard 白4（実機）
  → 黒5: 攻め側フィルタ（§2）で ≤12本
    → hard 白6（実機）
      → 黒7: 攻め側フィルタで ≤20本
        → トラップチェック:
           hard 白8（実機） + 黒の強制勝ち判定 = VCF(depth16/5s/500k) ∪ VCT(depth6/5s/500k)
           → 強制勝ちあり ⇒ トラップ候補
             → 【実機再検証ゲート】hard を本番 timeLimit=10s で再実行し、
               同じ白8を選び強制勝ちが残る場合のみ severity-A 確定
               （solid/perf/issue 全レビューの共通 blocker: 短縮 timeLimit の
               アーティファクトを閾値カウントに入れない）
```

- **severity-A** = 実機 hard の選択が強制負けを許す（= 人間が再現可能な必勝ルート）。
- **severity-B（hard は回避するが候補上位に地雷）は初回実行から除外**
  （perf blocker: プローブ反復で予算2〜3倍化 / issue 指摘: 決定的 hard では B は
  現状 live でない。同格手ランダム化を導入する際に再訪）。

## 5. コスト（perf レビュー blocker 反映: 仮定でなく実測で確定）

- 1チェックの最悪コスト = hard 3s + VCF 5s + VCT 5s = **13s**（v1 の 8s は VCF 未計上で誤り）。
  ただし序盤の詰みなし局面はプローブが早期に探索し尽くして返る公算が高く、平均は
  大幅に小さい可能性もある。
- **本実行前に代表 ply-7 局面 30 点で1チェック平均時間を実測**し、全体規模
  （ルート数 × B5 × B7）を「6並列 ≤12h」に収まるよう逆算して確定する。
  v1 の机上計算（6,240 チェック）は上限の目安に格下げ。
- hard timeLimit 短縮（レバー）: まず**序盤局面での hard の実所要を実測**。
  depth7/1M ノード上限で自然に 3s 未満なら短縮レバー自体が不要（perf S1。
  「3s に切ると選択がズレるか」の検証はレバーが必要になった場合のみ）。
- 並列: **チェック粒度のワークスティール**（珠型静的分割はストラグラーを招く。
  match.ts の nextTask カウンタ方式を踏襲）。worker は gate3 方式の直接 wasm ロード
  （bridge worker 不要・TT はインスタンス毎で共有ハザードなし）。
- 対称正規化 dedup は**ボーナス扱い**（予算計算に依存させない。石が対称軸を壊すと
  縮退するため）。

## 6. 対称正規化と事前登録の判定基準

- **canonical key の定義**（solid blocker 反映）: 盤面の225セル文字列 + 手番を、
  盤の8対称変換（D4 群: 恒等・回転3・鏡映4）すべてに適用した際の辞書順最小値。
  dedup は **global-D4**（カバレッジ正確を優先）。統計の珠型帰属は first-seen の
  ルートラベルとし、doc に「帰属は近似」と明記。実装は独立ユニット
  （変換の群性・全対称局面の同一キー・非対称局面の相違をユニットテストで固定）。
- **判定基準（事前登録）**: severity-A（実機再検証済み）の **canonical ply-8前局面**
  （= hard が敗着を打つ直前の局面のカノニカルキー）で数えて:
  - **5 局面以上** → 序盤定石ブック化（第2施策）に進む（トラップ回避焼き込み +
    同格手ランダム選択 = 決定性搾取の解消も同時に獲得）
  - **1〜4** → regression レジストリ追加 + 該当系統の個別対応。第2段の結果も見て再判断
  - **0** → 現状維持（texel-r2 + レジストリ運用）
- severity-B は閾値カウントに含めない（初回は収集自体しない）。

## 7. 実装要件（TDD・再利用 SSoT）

- **再利用**（solid S1、名指し）: 珠型 = `opening.ts` の `getAllJushuNames()` /
  `getJushuPositions()`。周囲2マス = `moveGenerator.ts` の `isNearExistingStone()`。
  候補ランキング = `searchEngine.ts` の `findBestMoveForReview()`（candidates[]）。
  強制勝ち判定 = **`regression-positions.ts` のチェックコアを共有ヘルパーに抽出**
  （scripts/lib へ。別実装だと registry へ戻すとき判定がドリフトするため SSoT 化）。
- **E2E アドミッションテスト（issue blocker 反映・go/no-go ゲート）**:
  ボス実戦ライン（雲月 → 白4 → **H7** → 白6 → **I7**）の黒手2つが攻め側フィルタを
  通ることをテストで固定する。注意: **texel-r2 で J6 は解消済みのため「severity-A
  として出現すること」はテストにできない**（hard の白手も r1 時と変わる）。
  テスト対象はフィルタの通過性のみ。加えて r1 重み（旧値をテスト内で setEvalParam
  注入）で当該 ply-7 局面のチェックを走らせれば「r1 なら severity-A になる」ことも
  固定できる（任意・可能なら）。
- ユニットテスト: 対称正規化（群性・カノニカル一致/相違）、フィルタ（H7/I7 通過、
  明白な非脅威手の除外）、severity 判定（既知ケース）。
- 出力スキーマに **provenance**（top-K 枠 / ランダム枠 / 脅威フィルタ通過フラグ）を
  含める（フィルタの取りこぼし評価と §8 の限界主張の裏付け）。

## 8. 限界の明記

- 強制勝ち判定は VCF(16) ∪ VCT(6) 予算 — これより深い罠は検出対象外（原調査と同一
  基準なので「J6 級」までは対称に拾える）。
- 攻め側フィルタによる取りこぼし — ランダム枠・脅威フィルタ・provenance 記録で緩和
  するが完全網羅ではない（存在証明はできるが不在証明はしない）。
- 短縮 timeLimit を使う場合の選択ズレ — severity-A は実機 10s 再検証ゲートで確定
  するため、閾値判断には乗らない（見逃し方向のリスクのみ残る）。
